# Validation

How the SDK checks a level against the format's rules, repairs what can be repaired and reports what cannot

Validation is a tool you call, it is not built into saving or loading. The game decides where to run it: opening a level in the editor reports problems, and playback skips the check. So the cost of validation is how long an author waits, never how long a player waits

## Three passes

| Pass | What it asks | Runs on |
|---|---|---|
| `RuleAnalyzer` | is each value in its range, not null, a known enum member | any root |
| `LevelGraphAnalyzer` | do the objects agree with each other | `Level` only |
| `PublishReadinessAnalyzer` | may the level be handed to strangers under a given profile | `LevelMeta`, optionally `Level` |

## ValidationFacade

`ValidationFacade` is the one entry point, so a caller does not need to know how many passes there are:

| Method | What it does |
|---|---|
| `Validate(root, settings)` | checks any root: `Level`, `LevelMeta`, `UserSettings`, a standalone `Prefab` or `EffectData`. The graph pass runs for a `Level` only |
| `ValidateAndFix(root, analyzerSettings, fixerSettings)` | repairs what can be repaired, then reports what is left |
| `ValidateForPublish(meta, profile, level, now, payload, settings)` | all three passes at once, repairs nothing. `level` may be `null` to grade the metadata alone |

```csharp
var facade = new ValidationFacade();
var report = facade.Validate(level);

if (report.HasErrors)
    Console.WriteLine(report);
```

`ValidationReport` holds `RuleIssues` and `GraphIssues`. `IsValid` means no findings at all, `HasErrors` means at least one finding of the `Error` group

## Severity

Every rule belongs to a `RuleGroup`:
- `Error` - the file cannot be played as written
- `Warning` - it plays, but not as authored (content that never appears, a broken reference taking a fallback), or the only repair is destructive
- `Advice` - playback does not change

## Rules

A type joins the check with the `[RuleContainer]` marker, and its properties carry rule attributes: `[RuleNotNull]`, `[RuleInRange]`, `[RuleMinValue]`, `[RuleEnumValid]`, `[RuleEnumFlagsValid]` for flag enums, `[RuleCollectionMaxCount]` and others. A member that may be absent is marked `[RuleOptional]`. The limits themselves are constants in the `Rules/` tables: `FrameRules`, `ValueRules`, `LevelRules` and others. For example, `LevelRules.MaxObjects` is 262 144

The walk over all rule containers is generated by `BH.SDK.Roslyn`, not done by reflection, which roughly halves its time on large levels

## Fixers

Every rule attribute knows how to repair its own value (`Fix`). `RuleFixer` applies repairs in reverse order of the trace, because a repair can shift deeper findings, and `ValidateAndFix` repeats the pass until the result stops changing. The graph pass runs after the repairs, since a repair can itself create a graph problem, for example a new id colliding with an existing one

Graph findings are never repaired: `DuplicateObjectId`, `MissingParent`, `ParentCycle`, `PrefabRemapBroken`, `IdCounterNearExhaustion` and the rest. Each repair of that kind is a content decision (which of two objects keeps its id), and a guess would rewrite the level

> [!caution] Caution
> `ValidateAndFix` changes the object you pass in. Run it on a copy when you need the original, for example to show the author what exactly was changed
